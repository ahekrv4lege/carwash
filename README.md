# Администратор автомойки: Telegram-бот + Google Sheets + AI (aiogram 3)

Telegram-бот работает администратором автомойки: клиент пишет обычным текстом («запишите меня
на мойку завтра в 10»), бот уточняет автомобиль и услугу, называет точную цену и свободное время,
а после нажатия «Подтвердить» под актуальной сводкой создаёт строку записи в Google-таблице.

Главный принцип: **нейросеть не знает цен и расписания и не считает ничего сама**.
У неё есть инструменты (tool calling); цены, скидки, слоты и запись выполняет Python по данным
Google-таблицы. Модель только понимает клиента и пересказывает готовые результаты.

---

## 1. Схема работы

```
   Клиент ◄──► Telegram (bot.py) ◄──► Agent (ai.py) ◄──► провайдеры AI (providers.py)
                                    │    промпт, история,     │ Polza: DeepSeek V4.1 Flash (open-inference/fp4)
                                    │    петля инструментов   ▼
                                    │                    вызовы инструментов
                                    ▼
                              Store (sheets.py)  —  прайс, тарифы, слоты, записи
                                    ▲
              adaptive.py (карта областей, валидация строк, честные отказы)
                                    ▲
                              Google-таблица: Услуги / Тарифы / Слоты / Записи / Классы
```

Путь одного сообщения:

1. **`bot.py`** (aiogram) принимает сообщение. Несколько быстрых сообщений подряд склеиваются
   в одно (`MessageBatcher`, задержка `REPLY_BATCH_SEC`) — нейросеть не дёргается трижды.
   Работают только личные чаты; есть `/start` и `/reset`.
2. **`ai.py` (Agent.reply)** собирает контекст: системный промпт (роль «Светланы», дата/время,
   правила поведения), `CUSTOMER` (факты клиента с цитатами), `STATE` (автомобиль, телефон,
   каталог, текущий расчёт, стадия) и историю диалога.
3. Запрос уходит в OpenAI-совместимый API (`providers.py` ведёт основную и резервные цепочки).
4. Модель отвечает вызовами инструментов; **`ai.py` исполняет их через `sheets.py`** и возвращает
   ей результаты. Это петля (`_run`): модель → инструмент → результат → модель → текст.
   Петля ограничена: `AI_MAX_TOOL_ITERATIONS` (6 шагов), `AI_MAX_TOOL_CALLS` (12 вызовов).
5. Готовый текст идёт клиенту (разбивается по лимиту Telegram 4096).
6. Предложение записи не создаёт строку. Клиент видит полную сводку и одну кнопку «Подтвердить».
   Исправления пишет в чат. Только подтверждение актуальной сводки записывает заказ; затем бот уведомляет
   администратора (`admin.py`).

## 2. Google-таблица: что нужно завести

Названия листов задаются в `.env` (`SHEET_*`), ниже — имена по умолчанию.

### «Услуги» — прайс, классы = колонки цен

| Услуга | Описание | Легковой | Кроссовер | Доступна |
|---|---|---|---|---|
| Мойка | Кузов | 700 | 800 | да |
| Воск | Защита | 200 | 300 | нет |

Каждая колонка кроме «Услуга/Описание/Доступна» — габаритный класс. Строка с «Доступна = нет»
убирает услугу из предложений, но не из таблицы. Нулевая цена допускается, отрицательная
и текстовая отбрасываются (услуга «не оказывается» для этого класса).

### «Тарифы» — комплексные предложения

| Тариф | Состав | Скидка % | Доступен |
|---|---|---|---|
| Базовый | Мойка, Воск | 10 | да |

Цена тарифа = сумма доступных услуг состава минус скидка. Услуга из состава, отсутствующая
или недоступная, честно показывается клиенту как «сейчас без: ...» с пересчитанной ценой.

### «Слоты» — расписание постов

| Дата | Время | Постов |
|---|---|---|
| 01.01.2099 | 10:00 | 2 |

Дата `ГГГГ-ММ-ДД` или `ДД.ММ.ГГГГ`, время `ЧЧ:ММ`, целое число постов. Дубль строки одной пары
дата/время складывает вместимость. Также поддержан «сеточный» формат листа «Пост 1 / Бокс 2»,
датированный в названии листа.

### «Записи» — журнал, бот пишет его сам

Колонки: `ID, Создано, Дата, Время, Имя, Телефон, Автомобиль, Класс, Тариф, Доп. услуги,
Состав, Сумма, Комментарий, Telegram ID, Username, Статус`. Правьте аккуратно во время работы
бота: изменение структуры этих колонок требует перепроверки mappings.

`ID` — постоянный номер записи: он выдаётся один раз при создании (максимум среди известных + 1)
и никогда не меняется — ни при сортировке, ни при отмене или переносе других записей. Именно по
нему клиент и администратор ссылаются на запись. Порядок строк в листе — только оформление:
новые записи дописываются в конец, хронологическую сортировку бот выполняет при периодическом
обслуживании (раз в 6 часов) и только если это безопасно — при формулах в данных или значениях
правее шапки сортировка пропускается с записью в журнал, чтобы не разрушить их.

### «Классы» (лист необязателен) — правила для машин с несколькими классами

| Автомобиль | Класс |
|---|---|
| BMW X5 | Кроссовер |
| Toyota LC 80 | Внедорожник |

Автомобиль, подходящий под несколько категорий (BMW X5 — кроссовер или внедорожник), заодно
это же правило снимает у клиента вопрос о категории: нейросеть выбирает класс **автоматически,
без лишних уточнений**. Правила передаются модели через `get_price_list` (поле `class_rules`)
и описаны в промпте. Порченные правила отбрасываются с предупреждением: класс не из прайса,
пустые ячейки, один автомобиль с разными классами. Название листа переопределяется
`SHEET_CLASSES`, без листа бот работает как раньше.

## 3. Модули и их роли

| Файл | Назначение |
|---|---|
| `bot.py` | aiogram 3: приём сообщений, батчинг быстрых сообщений, `/start`, `/reset`, доставка ответов |
| `ai.py` | Агент: промпт, память, петля инструментов, подтверждение записей, защита от глупостей модели |
| `conversation.py` | Строгий разбор ответа модели (JSON/tool-вызовы) |
| `providers.py` | OpenAI-совместимые провайдеры: основной + запасные, общий бюджет запроса |
| `sheets.py` | Google Sheets и вся бизнес-логика: прайс, тарифы, свободные слоты, создание/отмена |
| `adaptive.py` | «адаптер» таблиц: карта областей (mappings), переоткрытие при сдвигах, валидация данных, правила записи |
| `admin.py` | лента диалогов и событий для админ-чата (карточка «клиент → бот», кнопка профиля) |
| `config.py` | чтение/валидация `.env` в объект `Config` |
| `run.py` | запуск: виртуальное окружение, зависимости, проверка настроек, блокировка и самовосстановление |
| `start.sh` / `start.bat` | оболочки для Linux / Windows |

## 4. Принципы и алгоритмы

### 4.1. Инструменты модели

Доступны восемь инструментов (`TOOLS` в `ai.py`):

| Инструмент | Что делает |
|---|---|
| `respond` | сохранить факты клиента (только с точной цитатой из его слов) |
| `reschedule_booking` | подготовить перенос своей записи с сохранением ID, состава и суммы |
| `get_price_list` | прайс: классы, `class_rules`, услуги, тарифы, недоступные позиции |
| `calculate_price` | точный расчёт (Python: `Catalog.quote` — тариф + доп. услуги + скидка) |
| `get_free_slots` | свободное время на дату |
| `create_booking` | предложить запись (см. 4.4) |
| `cancel_booking` | предложить отмену собственной записи |

Полная цена всегда считается в Python. Модель, назвавшая цифру без вызова
`get_price_list`/`calculate_price`, ловится специальной проверкой (`price_without_verified_catalog`).

### 4.2. Память с цитатами

Каждое сохранённое поле — `[значение, точная цитата]`. Python проверяет, что цитата реально
есть в словах клиента, иначе факт отбрасывается. Это защита от «нейросеть что-то выдумала».
Сомнительное («или», «наверное») уходит в `tentative` и не бронируется. Позднее слово в том же
сообщении побеждает более старое; автомобиль сохраняется как сказал клиент, распознанная
марка/модель — в `car_model` (в запись идёт только исходный текст).

### 4.3. Батчинг и «человеческий» темп

`MessageBatcher` (0,4 с) собирает серию быстрых сообщений в одно. Минимальная пауза ответа
(`REPLY_MIN_DELAY_SEC`, 1,5 с) задаёт человеческий темп; `Agent` держит состояние каждого диалога
(TTL 1 час, максимум 1000 сессий). Телефон маскируется в переписке и истории (`redact_phone`),
но в запись идёт целиком.
Сообщения и нажатия кнопок обрабатываются по очереди для каждого клиента. Текстовое
согласие лишь напоминает о кнопке; актуальность сводки и доставку проверяет обработчик нажатия.

### 4.4. Подтверждение записи (двухфазная запись)

Запись никогда не появляется по первому требованию модели:

1. Модель вызывает `create_booking`; Python проверяет аргументы против `CUSTOMER`:
   каждое поле должно исходить от клиента (или быть следствием названного автомобиля —
   исключение для `size_class`, который подбирается по правилам прайса).
2. **`_prepare`:** свежий срез таблицы — пересчёт цены, проверка свободного времени.
   В таблицу пока ничего не пишется. Клиент получает полную сводку и одну кнопку «Подтвердить».
   Предложение старше 10 минут → «устарело, проверим заново».
3. Исправление обычным сообщением снимает старое предложение; остальные данные сохраняются.
   После изменения бот готовит новую сводку. Только кнопка «Подтвердить» на доставленной
   актуальной сводке подтверждает действие; текстовое «да» не создаёт запись.
4. **`_confirm` пересчитывает всё заново:** если цена/состав изменились между предложением
   и подтверждением (админ поправил прайс), клиент получает новое предложение, а не новую цену.
5. Проверяются: дубль записи того же клиента на то же время/автомобиль, свободные места
   (Постов − занято), возможные формулы в строке записи. Только после этого — строка в таблицу
   через write-preflight (адресная запись, проверка формул и прав области).
6. Квитанция сохраняется в STATE: повторные и устаревшие нажатия не создают дубликат.

Если результат записи неизвестен (обрыв сети во время записи) — бот честно переводит
диалог в «uncertain» и никогда не повторяет операцию автоматически.

### 4.5. Адаптивный слой: кривые таблицы не портят данные (`adaptive.py`)

Для новой таблицы укажите её `SPREADSHEET_ID` в `.env`, откройте сервисному аккаунту
доступ и запустите `python run.py --new-table`. Бот сначала создаст отдельную карту,
проверит структуру и данные и запустится только при доступной безопасной записи.
Карты других таблиц и журналы операций сохраняются. Если таблица требует настройки, бот
не запустится, а путь к созданной карте для проверки будет выведен в консоль.
Для того же `SPREADSHEET_ID` команда заново распознаёт таблицу и заменяет её карту
только после успешной проверки; журнал операций остаётся на месте.
При следующих обычных запусках карта этой таблицы выбирается автоматически;
явный `SHEETS_ADAPTIVE_ENABLED=false` отключает адаптивный режим.

Google Sheets возвращает сырые строки без пояснений. Адаптивный слой делает из этого
нормальные данные:

1. **Снимок** (`_snapshots`): вся таблица в двух видах — FORMATTED (то, что видят) и FORMULA
   (сырье формул). Границы: лист > 1 млн клеток → отказ.
2. **Карта** (`discover`): шапки распознаются по алиасам (`ALIASES`: «телефон»/«phone»/«тел»).
   Область узнана, только если есть обязательные для роли поля (`READ_REQUIRED`).
   Две колонки с одним смыслом или две области одной роли — отказ, а не угадывание.
   Целые 20-строчные выборки определяют, какие колонки — цены; классы вне белого списка
   требуют ручного решения. Незнакомый лист попадает в `issues` (журнал), не мешая четырём ролям.
3. **Сверка на каждом чтении**: хеш структуры (fingerprint) сверяется с сохранённым.
   Колонки переставили — `_relocate` находит их по заголовкам и алиасам (клиент ничего
   не замечает). Заголовок переименовали без совпадения с алиасом — область становится
   «нечитаймой», бот честно отказывает и требует перепроверки mappings, вместо чтения кривого.
4. **Санобработка** (`_extract_records`): даты (строка/формат/serial Google), время (9.30 → 09:30),
   статусы (done/выполнено → «Выполнена»), слоты сеткой, канонические имена полей.
   Битая дата или время дают отказ с понятным текстом («Дата не соответствует выбранному
   преобразованию»), а не кривые данные клиенту.
5. **Валидация значений** (`_validate_records`): отрицательные/текстовые цены, скидки > 100%,
   дубликаты услуг/тарифов/ID, «Постов = 1.5» — всё отказывается с точным сообщением.
6. **Права записи** (`_summarize`): писать можно только в полностью подтверждённые области.
7. **Память**: карта хранится в `.runtime/sheets-mapping.json`; сохранение атомарное
   (временный файл + rename). Файл с изменённой подписью/версией не загружается.

Итог: **неудача всегда оборачивается отказом, а не выдуманным значением** — клиенту не может
показаться цена, которой нет в таблице.

### 4.6. Правила классов автомобилей (лист «Классы»)

Машина как BMW X5 подходит под несколько категорий. Правило из листа «Классы» читается вместе
с прайсом (`class_rules`), передаётся модели и описывается в промпте: «выбери класс по правилу
сам, клиенту вопросов не задавай». Офлайн-функция `Catalog.resolve_class_rule` решает правило
детерминированно (точное совпадение → совпадение по части имени; противоречивые правила
одинаковой модели игнорируются). Проверено тестом полного сценария записи без уточнений.

### 4.7. Провайдеры AI с запасными

Текущий основной маршрут — Polza, DeepSeek V4.1 Flash через `open-inference/fp4` без
резервного провайдера (`allow_fallbacks=false`). Другие совместимые API и резервные маршруты
поддерживаются настройками, но не включены в текущий `.env`. Код также поддерживает второй
ключ (`LLM_API_KEY_2`) и до трёх резервных маршрутов (`LLM_FALLBACK_N_BASE_URL/_API_KEY/_MODEL`);
при их настройке запрос переносится на следующий маршрут при rate limit, исчерпании квоты или недоступности.
Запрос ограничен бюджетом времени (`AI_REQUEST_BUDGET_SEC`); порог срабатывания учитывает шаг
таймера Windows.

В рабочем `.env` временно установлен `reasoning_effort=low` и заданы ограничения цены:
`LLM_MAX_INPUT_RUB=5.1`, `LLM_MAX_OUTPUT_RUB=1.2` (рубли за миллион токенов).
Код преобразует alias в обычный запрос Polza и добавляет `provider.max_price`.
Если маршрут подорожал выше предела или недоступен, запрос завершится ошибкой;
дорогой провайдер автоматически не подключится. Для другой модели пределы нужно пересмотреть.
`AI_REQUEST_BUDGET_SEC` ограничивает весь ответ с инструментами; `AI_TIMEOUT_SEC` — отдельный вызов.

### 4.8. Чат администратора

`admin.py` (`ADMIN_CHAT_ID`): карточка каждого обмена «клиент → бот» (общее окно 3500 символов)
и уведомления о записях/отменах; кнопка «Открыть профиль». Ошибка отправки админу не роняет бота.

## 5. Установка и запуск

Требуется Python 3.10+. На Windows — галочка «Add Python to PATH».

```bash
# 1. Настройте .env (см. таблицу ниже) и положите credentials.json
# 2. Запуск:
python run.py            # автоматически: .venv, зависимости, затем бот
# или одним файлом:
start.bat                # Windows
./start.sh               # Linux/macOS

python run.py --check    # локальная проверка настроек, без сети
python run.py --doctor   # авторизация Telegram и чтение Sheets, без платного AI
```

`run.py` сам создаёт виртуальное окружение, устанавливает зависимости (`requirements.txt`),
проверяет конфигурацию и питон-версию, берёт блокировку от второго экземпляра того же проекта и
перезапускает бота при падении (пауза 5 с). Логи — в stdout.

Фоновый хостинг и автозапуск одной командой из папки проекта:

```bash
./start.sh --host    # Linux с systemd
```

На Windows: `start.bat --host`. Команда подготавливает зависимости, проверяет Telegram и
таблицу, затем создаёт службу пользователя systemd или задачу Windows при входе в систему.
Токен не попадает в командную строку службы: бот читает локальный `.env`.
Linux-служба сохраняет настройки прокси текущего окружения. При включённом linger systemd
может запускать её до входа пользователя. Компьютер должен быть включён и не спать;
локальный прокси, если он нужен, тоже должен работать.

`./start.sh --status` показывает состояние, `./start.sh --logs` — журнал,
`./start.sh --stop` останавливает службу и выключает автозапуск. На Windows те же флаги
передаются `start.bat`; журнал хранится в `.runtime/host.log`.
Запуск Windows Task Scheduler требует отдельной проверки на настоящей Windows.

Telegram автоматически использует системный/заданный в окружении прокси.
`TELEGRAM_PROXY=direct` отключает его; `TELEGRAM_PROXY=http://127.0.0.1:7897` задаёт явно.
TLS-проверка сертификатов остаётся включённой.

Модель, ключи и ограничения цены задаются в `.env`. Текущий маршрут — дешёвый DeepSeek
с уровнем рассуждений `low`. Для `none` код передаёт Polza `reasoning.enabled=false`;
этот вариант ещё не проверен на живом запросе. Отдельные одинаковые профили больше не нужны; старый флаг `--profile`
принимается для совместимости с установленной службой.
Диалог, распознавание автомобиля и ответы на вопросы ведёт модель. Создание, перенос
и отмена записи исполняются кодом после кнопки. API-запрос и весь ответ с инструментами ограничены
общим пределом в 5 минут.
Это предел ожидания, а не задержка перед ответом: готовый ответ отправляется сразу.
После обычного сбоя единственный API не блокируется на минуту: пауза составляет 2 секунды;
явный `Retry-After` провайдера соблюдается.

Перенос меняет дату и время существующей строки одним запросом; ID, цена и услуги
сохраняются. Перед нажатием и перед записью проверяются владелец, исходные данные и
занятость. Перенос между отдельными областями дат адаптивной таблицы требует администратора.

Что положить рядом с кодом (в git эти файлы не попадают):

- **`.env`** — токены и настройки (см. справочник ниже);
- **`credentials.json`** — ключ сервисного аккаунта Google (Google Cloud Console →
  Service account → JSON key), доступ к таблице открыт по `SPREADSHEET_ID`.

## 7. Ограничения и договорённости

- Бот — один процесс: локальные блокировки защищают от конфликтов его же операций; правки таблицы
  внешними редакторами параллельно с записью проверяются на лету, и при конфликте запись
  откладывается с честным объяснением.
- Модели недоступен «выход в интернет» — только перечисленные инструменты.
- Работа с записями: только свои (`Telegram ID` совпадает), отмена — только по заявке клиента.
- Личная информация: телефон маскируется в переписке и истории; ключ сервисного аккаунта
  храните только в `credentials.json` вне git.
